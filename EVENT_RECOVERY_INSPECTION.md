# Bounded read-only event recovery inspection

## Endpoint and scope

GET /api/recovery/status?camera_id=<registered-id>&staging_id=<event-directory-basename> inspects exactly one known direct child of that camera's temp directory. It does not enumerate staging, choose an event by a legacy camera name, or create a recovery browser. staging_id must match event- followed by 1-80 ASCII letters, digits, underscores or hyphens. Exactly one value of each parameter is required, with no other query keys. The operator currently obtains the staging basename from their own filesystem inspection. This parameter is not a recovery authorization token.

The endpoint uses existing browser-session authentication; event-only bearer tokens do not authorize it. Unknown camera returns 404, invalid queries 400, and non-GET 405. Missing/unavailable staging returns an incomplete 503 report, not a claim that recovery data does not exist. Cache-Control is no-store and X-Content-Type-Options is nosniff. Storage-status and recovery-status share the same two-slot inspection semaphore, so combined admitted work is bounded to two requests. Excess work returns 503 with Retry-After.

A five-second cooperative context covers inspection. The new route participates in shutdownGate cancellation and joining before final persistence. Filesystem calls may block beyond the cooperative deadline; no goroutine is abandoned to fake timeout completion. Camera pointer/directory snapshots are revalidated before responding; replacement/removal/path changes produce an incomplete report. This is not a transaction with external filesystem changes or configuration mutation outside the normal registry locks.

## Manifest validation

Only recovery.json is read, at most 64 KiB plus one sentinel byte, twice to detect manifest-content changes. UTF-8, a token/depth budget, duplicate keys at all object levels, exact case-sensitive known/required keys, nulls, trailing JSON, version, positive bounded revision, camera/event identity, requested duration/range, required timestamps, state/failure-code combinations, pin count, generated input names and safe output-name relationships are validated. At most 128 prebuffer inputs are allowed. Version 1 revisions above 1000000 are conservatively rejected; the current finite lifecycle does not approach that bound. Unsupported or inconsistent manifests never become actionable instructions. The reader does not relax these checks to make hand-edited or legacy artifacts appear valid.

Initial pinning and failed-prefix pinning are distinguished from completed pinning. The manifest's requested range is caller intent, not actual acquisition coverage. Metadata times and observed checkpoint times are not calibrated camera timing. A published output name can represent intent, particularly in publishing state; the report does not infer success from a filename.

## Descriptor and resource boundaries

Camera root, temp and the named staging child are opened as no-follow directories. Child directories use descriptor-relative no-follow lookup/open with identity comparisons. recovery.json is inspected without following links, opened first as an O_PATH/O_NOFOLLOW identity descriptor and checked to be a regular file, then reopened through its own /proc/self/fd reference with O_NONBLOCK for bounded reading. The readable descriptor is revalidated against the verified inode before reading; a name swapped to a device/FIFO is not activated by the initial O_PATH open. Device/inode/type, size and timestamps are checked before/after reading and against the directory name. Linux procfs access is required; unavailable /proc/self/fd fails closed. Directory names are revalidated at completion. Context checks occur between operations; close errors also make the report incomplete.

Media and concat files are never opened/read or executed. Only no-follow metadata for the validated planned prebuffer names, fixed event.mp4/concat.txt, and validated root output names is observed. At most 132 artifact metadata observations are attempted. Symlinks and special files fail inspection rather than becoming zero-byte media or blocking FIFO reads. Root output lookup is metadata-only and does not attest ownership by the claimed event. Trusted parent paths remain an assumption. This is not a filesystem-wide scan, an atomic multi-file snapshot, a hostile-filesystem sandbox or media validation. Filesystem-managed access times can change when the manifest is read; read-only means no application writes or recovery mutations.

Temporary recovery-*.json.tmp snapshots are preserved but not read, counted or treated as authoritative by this endpoint. Unrecognized files and nested directories are not enumerated. Use the separate bounded staging usage endpoint for storage accounting. The reader is deliberately separate from admission scanning, so enabling inspection does not make recording admission parse JSON.

## Response meanings

The JSON report includes camera/staging IDs, observation time, inspection_complete, classification and fixed inspection error codes. A validated manifest can supply event ID, checkpoint state/revision, requested range/duration and checkpoint_partial. Artifact observations contain roles, prebuffer indexes, presence and logical size only when known. No absolute paths, RTSP URLs, credentials, labels, input/output filenames or media bytes are returned. Successful independent observations can remain in an incomplete report; a failed observation is omitted rather than invented as absence or zero.

Classifications are legacy_or_missing_manifest, invalid_or_unsupported_manifest, inflight_or_interrupted, observed_processing_failure, publication_outcome_ambiguous, published_checkpoint_unverified, or inspection_incomplete. A missing manifest may be legacy staging, an interrupted initial write or a live job not yet checkpointed; it is not permission to delete. Unknown camera identity, malformed JSON and unsupported versions are deliberately grouped into manifest rejection rather than trusting their unvalidated fields.

HTTP 200 means the restricted inspection completed, not that capture succeeded, files are complete, a directory is inactive, or anything is safe to delete/reassemble. published_checkpoint_unverified can legitimately coexist with an absent output or a partial flag. Concurrent artifact growth/removal can occur between metadata observations even if manifest bytes are unchanged. Stale or untrusted checkpoints and files require independent operator review. HTTP 503 means incomplete/rejected inspection and must not be presented as proof of missing footage.

## Recovery and verification restrictions

Stop cleanly and preserve independent copies of configuration, event metadata and the whole affected camera directory before any manual recovery. There is no repair, retry, expiry, deletion, migration, FFmpeg probe or reassembly action in this batch. Do not execute retained concat lists. Validity of the manifest is not validity, completeness or recoverability of footage.

Regression drafts cover schema ambiguity/cross-camera rejection, writer checkpoint round-trips, read-only artifact checks, missing-manifest handling, symlink/FIFO/directory rejection, request validation, capacity/slot release, camera replacement, real session-versus-bearer scoping and shutdown join-before-persistence. These tests have not been compiled or executed by the assistant: Go and gofmt are unavailable in the preparation environment. Real blocked mounts, disk/inode exhaustion, power loss, full live-camera capture and real-browser behavior remain separate requirements. Keep the audit branch unmerged pending exact-commit CI, integration validation and final whole-branch review.
