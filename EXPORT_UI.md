# Monitored browser exports

The Download modal's button calls startExportDownloads from export-ui.js, loaded after playback.js. The legacy direct-link startDownload function has been removed from playback.js, without a compatibility alias or fallback. Source regression guards reject legacy definitions/calls/references in static scripts and templates, and a JavaScript load test asserts that the old global is absent while the monitored entry point remains available. These guards are not a general JavaScript call-graph proof. No global renderer or download function is overridden.

Each batch snapshots its camera IDs/names and absolute requested range. Later selection/range edits do not alter queued requests. One to eight cameras can be monitored; duplicate starts share the existing batch. The modal remains open and shows per-camera queued, preparing, receiving, ready, handed, failed, canceled or expired states. Closing the modal only hides it; use Cancel or Cancel all to stop work. Page exit also cancels the batch.

The client checks HTTP status, MP4 content type, recognized range policy, response length when supplied, a nonempty body and the expected initial MP4 ftyp marker. Error excerpts are bounded to 2048 bytes/600 displayed characters. Missing coverage/overlap, authentication, missing media, unsupported trim/audio profiles, server limits and timeouts are displayed without offering an error document as a video file. Names, policy text and server excerpts enter only textContent; no toast HTML sink is used.

Only one file is received or retained as a prepared object URL at a time. The monitored receive cap is 64 MiB, independent of the backend's 256 MiB trim-render cap. Oversized declared or streamed responses are canceled and require a smaller range; there is no unbounded Blob fallback or automatic unmonitored retry. This caps application payload buffering, not browser-internal allocation overhead or Blob copies. Queued requests have not started while a file is prepared for hand-off.

Receiving is bounded by a four-minute client deadline and supports explicit cancellation during fetch/body reads. Prepared files expire after two minutes without hand-off. A user must click Hand received file to browser. That requests a browser download but does not establish that the browser accepted it or saved it to disk. The URL is revoked after 60 seconds, or earlier when the user chooses Release prepared file / continue after browser acceptance. Revocation/discard precedes starting the next camera. Cancellation cannot retract an already requested browser download.

The UI surfaces whole-clips-untrimmed versus decoded-video-frame-window and reported trim duration, including the frame-granular/video-only limitation. Receiving all response bytes plus an ftyp marker is not validation of media/container completeness. A producer that cleanly ends a truncated, unknown-length MP4 may still be undetectable here. The status therefore never claims successful disk saving or verified footage. Browser download restrictions, filesystem failures and authenticated slow-client integration remain unverified.

Node tests exercise the real module with stubbed DOM/fetch/streams: policy/status handling, text-only rendering, length/type/signature failures, declared-size rejection, sequential hand-off/revocation, range snapshots, pending-fetch/body cancellation, timeout and ready expiry. They are not full browser tests. Existing backend trim/audio/profile and metadata limits remain unchanged. Absolute-time/DST canvas geometry, restricted single-camera continuation and playback failure handling are implemented; see PLAYBACK_CONTINUATION.md and PLAYBACK_FAILURES.md. Opt-in storage/staging admission, authenticated storage status, recovery checkpoints and bounded read-only recovery inspection have focused documentation, including EVENT_RECOVERY_INSPECTION.md. They do not solve runtime disk-full behavior, validated recovery actions, browser disk saving or media completeness. Audio-aware trimming remains a scope decision. Real-browser/authenticated export integration, storage-failure validation and final whole-branch review remain required under AUDIT_ACCEPTANCE.md; keep the audit branch unmerged.
