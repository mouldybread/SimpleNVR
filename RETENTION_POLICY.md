# Retention bounds and fail-closed cleanup

API retention updates now accept 1 through 365 days, matching the existing UI limit. Persisted camera values accept the same range plus legacy 0, which still means seven days. Conversion to time.Duration occurs only after validation, preventing a large positive integer from wrapping into a negative deletion interval. For example, 106752 days exceeds the signed nanosecond duration range.

Configuration with negative or above-365 retention is rejected on load/save, not silently clamped or rewritten. This is a compatibility change for manually configured values above 365, including values that would otherwise fit time.Duration. Such deployments require an explicit policy correction before startup; preserve configuration/backups and evidence rather than assuming an automatic migration. Valid legacy zero-valued configurations remain loadable. A rejected load leaves the existing in-memory state and source file untouched; a rejected save does not replace the configuration.

As defense in depth, periodic cleanup skips published-file retention for cameras with invalid runtime values and preserves event metadata associated with their names. An invalid policy is not treated as a deleted camera. The lower-level published-file cleanup function also refuses nonpositive duration arguments. Valid retention still applies to published root MP4s, including published partial files. Root .tmp files and nested event staging retain their existing protections. Explicit camera deletion and manual orphan cleanup policies are unchanged.

Tests cover range boundaries, legacy zero, overflow-producing values, invalid single/bulk API updates without mutation, rejected load/save behavior, runtime media/event preservation and nonpositive duration rejection. This patch does not solve concurrent retention-policy snapshot changes, filename/wall-clock uncertainty, hostile filesystem replacement, staging quotas or disk-full recovery.
