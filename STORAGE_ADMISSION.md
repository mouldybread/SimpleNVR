# Opt-in recording storage admission

SIMPLENVR_MIN_FREE_BYTES is an unsigned decimal byte count. Unset or 0 disables this guard; existing deployments do not acquire a new default reserve. For example, 268435456 configures a 256 MiB pre-admission reserve. Unit suffixes, negative values, whitespace and overflowing values are rejected when recording admission is attempted.

With a nonzero reserve, a new continuous or event-based recording worker starts only if Linux statfs reports at least that much space available on the existing camera directory's filesystem. The HTTP event-trigger handler also checks the reserve before requesting an active event capture. The check uses Bavail, not total free blocks, and compares block counts without multiplying into an overflowing byte count. A missing/inaccessible camera directory or failed capacity query fails closed; there is no parent-directory fallback, directory creation or deletion.

Insufficient space maps to HTTP 507; unavailable capacity or invalid policy maps to 503. Recorder-start rejection occurs before allocating the recording context/wait-group worker or changing start intent. A failed startup resume retains loaded recording intent for a later explicit retry; this patch adds no automatic retry scheduler. Already-running idempotent starts are not rechecked. Explicit stops and transitions to no_recording remain available. Mode changes that would start a worker perform a preflight before stopping the old mode and check again at new-worker admission. If space changes between those checks, the replacement can still be rejected after the old worker stops.

For an active event-based camera, the HTTP handler checks storage immediately before BufferManager.TriggerEvent, before that call can reserve a slot, create staging, pin prebuffer files or queue capture work. A storage-rejected request neither appends event metadata nor invokes persistence. Metadata-only logging for non-capturing cameras bypasses the guard. Successful requests retain the existing asynchronous recording_queued semantics; admission is not proof that footage was saved. Direct internal BufferManager.TriggerEvent calls are not changed by this HTTP-boundary check.

This is a snapshot admission check, not a disk reservation, quota or runtime watchdog. Concurrent writers and admitted cameras/events can consume the same observed free space. Existing recorders' ongoing output, individual segments, queued event execution/assembly and exports are not newly bounded by this policy. Staging is never expired or deleted here. Inode exhaustion, write errors, filesystem stalls, durable recovery and a complete disk-full response remain unresolved. statfs runs within the recording-control critical section and cannot be canceled if the filesystem blocks; recorder-start checks also hold the registry lock, while the event handler releases its registry read lock first. The implementation targets the existing Linux deployment.

Tests cover configuration parsing, overflow-safe comparisons, low-space/unavailable recorder admission without worker allocation, restart-intent preservation, mode-change preflight, stop availability, disabled behavior and HTTP mapping. Event-handler tests use isolated NVR state and an injected persistence callback to cover rejected admission without metadata/slot/queue/staging side effects, preservation of existing recovery artifacts, admitted capture behavior and metadata-only bypass. Real disk exhaustion, reserved blocks for different service users, mount failure, concurrent-writer and live-camera capture integration are not simulated by these tests. Keep the audit branch unmerged.
