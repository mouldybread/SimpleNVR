# Authenticated per-camera storage inspection

GET /api/storage/status?camera_id=<registered-camera-id> is a read-only endpoint behind the existing browser-session authentication middleware. Event-only bearer tokens do not grant access. Exactly one nonempty camera_id is required; duplicate, unknown query keys and malformed queries return 400, unknown cameras return 404, and non-GET methods return 405. Results use Cache-Control: no-store. The response does not expose recording paths, camera names, RTSP URLs, credentials, filenames or directory contents.

At most two inspections run concurrently in this process. Additional work returns 503 with Retry-After. The handler uses a five-second cooperative context deadline and snapshots the camera directory under the registry read lock before releasing that lock for filesystem work. The endpoint participates in shutdownGate cancellation and joining before final persistence. No goroutine is abandoned merely to return a timeout; blocked syscalls can still exceed the cooperative deadline and the overall shutdown budget may report failure.

The JSON report includes camera_id, observed_at, inspection_complete, configured admission thresholds, available bytes on the camera directory's filesystem, free inodes when the filesystem reports an inode count, bounded staging logical bytes/direct-directory count and scan limits, and fixed inspection error codes. Capacity uses descriptor-based filesystem inspection; staging uses the existing no-follow descriptor-relative bounded scanner. Capacity and staging observations are separate and are not an atomic filesystem snapshot.

An unavailable capacity measurement or incomplete staging scan is omitted, never represented as a fictional zero. Valid independent measurements may remain present in a 503 report. Invalid configured thresholds are omitted with an error code rather than represented as disabled. Explicit configured 0 still means the corresponding admission policy is disabled. free_reserve_met and staging_below_limits are emitted only when their relevant policies are enabled and their measurements/configuration are known.

HTTP 200 means the requested inspection completed, not that storage is sufficient: a complete report can legitimately show a false threshold comparison. HTTP 503 plus inspection_complete=false means the overall report is incomplete or configuration is invalid. Neither result guarantees a recording can start, an event will be accepted, media was saved, or storage will remain available. Other recorder/queue limits still apply. Busy and request-validation failures may use plain HTTP error bodies; completed/partial inspections use JSON.

Status requests perform staging inspection even when staging admission thresholds are disabled, because inspection is explicitly requested. Large or unusual staging trees can therefore produce an incomplete status without changing the disabled admission behavior. Existing scanner entry/depth/no-follow limits and conservative logical-byte/hard-link accounting remain. No recording, event metadata, recovery file, policy or configuration is modified; there is no repair, deletion, reassembly or evidence-expiry action.

Tests include real filesystem accounting and threshold reporting, overflow/invalid-unit checks, strict request validation, saturated inspection admission and slot release, omission of unknown values, real auth session versus bearer-token scoping, and real shutdown-gate cancellation/join-before-persistence behavior. Tests do not simulate blocked mounts, real disk exhaustion or authenticated network slow-client behavior. There is no UI panel in this batch.
